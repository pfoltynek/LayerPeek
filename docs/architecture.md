# Architektura

## Přehled

LayerPeek je **tray-only** aplikace (Windows: oznamovací oblast, macOS: menu bar) bez hlavního okna. Z menu ikony lze otevřít jen pomocná okna (nastavení, diagnostika, kamera).

```
┌───────────────────────────────── LayerPeek.App (Avalonia) ────────────────────────────────┐
│  TrayIcon + NativeMenu │ ViewModels │ pomocná okna │ platformní služby (notifikace, autostart) │
└───────────────┬───────────────────────────────────────────────────────────────────────────┘
                │ DI (composition root)
┌───────────────▼──────────────┐   ┌──────────────────────────────┐
│ LayerPeek.PrusaLink          │   │ LayerPeek.PrusaConnect       │
│  REST klient (lokální síť)   │   │  cloudový klient             │
└───────────────┬──────────────┘   └───────────────┬──────────────┘
                └──────────────┬───────────────────┘
               ┌───────────────▼───────────────┐
               │        LayerPeek.Core         │
               │ doménový model, IPrinterClient│
               │ monitoring, detekce událostí  │
               │ abstrakce (INotificationService, ISecretStore…) │
               └───────────────────────────────┘
```

## Pravidla vrstev

- **Core** nezná Avalonii ani konkrétní HTTP API. Obsahuje doménu, rozhraní a logiku (polling, detekce událostí).
- **PrusaLink / PrusaConnect** implementují `IPrinterClient`; DTO (tvar JSON) jsou oddělené od doménových modelů.
- **Camera.FFmpeg** (T-014) implementuje `ICameraFeedFactory` z `Core/Cameras`: RTSP/H.264 přes FFmpeg (FFmpeg.AutoGen, P/Invoke) a převod snímků na BGRA. Závisí jen na Core (`App -> Camera.FFmpeg -> Core`). Nativní knihovny FFmpeg 9.0.2 (LGPL 3+) obstará `build/FFmpeg.targets` při buildu: pro `win-x64` stáhne a ověří build BtbN (připnutá URL + SHA256), pro `osx-arm64` stáhne a ověří oficiální zdrojový tarball a přeloží ho skriptem `build/macos/build-ffmpeg.sh` (T-026). Na macOS mají knihovny názvy podle install name (`libavformat.63.dylib`); `FFmpegRuntime` názvy bindingu (`avformat-63`) převádí přes `NativeLibrary.SetDllImportResolver` a načítá je jen ze složky aplikace (nikdy z Homebrew). Znovupřipojení, timeouty a stav připojení řeší `Core/Cameras/ReconnectingCameraFeed`; App jen vykresluje snímky do `WriteableBitmap` (okno kamery, malý náhled).
- **App** je composition root: registruje služby, implementuje platformní rozhraní, zobrazuje stav. UI pouze odebírá snapshoty z monitorovací služby.
- **tools/PrusaSimulator** (T-045) je samostatný vývojový nástroj mimo aplikaci: simulované tiskárny PrusaLink (Kestrel ze sdíleného frameworku ASP.NET Core) a RTSP kamera Buddy3D. Nereferencuje kód aplikace (tvar API napodobuje podle fixture), nepublikuje se s aplikací a neprochází AOT analýzou. Kameru simulátoru používají i testy FFmpeg. Návod: [simulator.md](simulator.md).

## Tok dat

1. `IPrinterMonitor` (Core) periodicky volá `IPrinterClient.GetSnapshotAsync` pro každou tiskárnu.
2. Nový `PrinterSnapshot` se publikuje odběratelům (tray ikona, menu, diagnostika).
3. Detektor událostí porovná předchozí a nový snapshot a při změně (dokončeno, chyba…) zavolá `INotificationService`.
   - `Core/Events/PrintEventDetector` je čistý stavový automat (bez I/O). `Core/Notifications/PrintEventNotifier` odebírá `IPrinterMonitor.SnapshotUpdated`, filtruje události podle `NotificationSettings` a volá `INotificationService` (T-009).
   - App předává nastavení každého běhu přes `IMonitoringObserver.ApplySettings` (`App/Notifications/PrintNotificationObserver`).
4. Na Windows je `INotificationService` = `App/Notifications/ToastNotificationService` (T-010): `Show` jen zařadí notifikaci do omezené fronty, vlastní vlákno sestaví XML toastu (`ToastContentBuilder`) a zobrazí ho přes WinRT (`Platform/Windows/WindowsToastPlatform`, vlastní interop přes `[GeneratedComInterface]`). Jazyk textů se určí jednou pro každý toast těsně před sestavením (`UiLanguage.CurrentTextCulture`, viz bod 10) a všechny texty toastu se čtou přímo v něm (`ToastContentBuilder.Build(notification, culture)`), takže přepnutí jazyka platí hned pro další toast a jeden toast nikdy nesměšuje jazyky. Zvuk (`PlaySound`) a název tiskárny v titulku určuje `PrintEventNotifier` podle nastavení aktuálního běhu: změna jen upozornění (např. zvuku) přijde bez restartu monitoringu přes `UpdateSettings`, přejmenování tiskárny restartuje běh a přijde přes `ApplySettings`; obojí platí pro další toast. Na macOS je `INotificationService` = `App/Notifications/UserNotificationService` (T-020) nad `UNUserNotificationCenter` (vlastní interop na Objective-C runtime, `Platform/MacOS/MacUserNotificationCenter`): stejné texty jako toast (`ToastContentBuilder.Lines`: titulek = tiskárna, text = událost a na druhém řádku soubor nebo teploty), stejný zvuk (`PlaySound`, výchozí zvuk systému) a stejný argument kliknutí (`ToastLaunchArgument` v `userInfo`). O oprávnění se žádá až s první notifikací (ne při startu) a před každou další se ověří znovu, takže povolení v Nastavení systému platí hned. Kliknutí hlásí delegát registrovaný za běhu (`objc_allocateClassPair`), nastavený v `Program.Main` ještě před dokončením startu AppKitu; jde přes frontu příkazů instance (`InstanceCommand` „toast“) do `ToastActivationRouter` jako na Windows. Na ostatních OS a bez centra notifikací (vývojové sestavení bez bundlu, testhost, jiný bundle) je zaregistrovaná `NullNotificationService`. Okno Nastavení vidí stranu OS přes `ISystemNotificationSettings` (`SystemNotificationSettingsOption`; T-020, T-101): na macOS `MacNotificationSettings` nad stejným centrem (stav oprávnění, `requestAuthorization`, zkušební upozornění), na Windows `ToastNotificationSettings` nad `ToastNotificationService` (čtení `ToastNotifier.Setting` a zkušební toast jako požadavek na vlákně toastů, otevření `ms-settings:notifications`), jinde žádná (bez tlačítka testu). Zkušební upozornění má pevný identifikátor / tag `TestNotification.Identifier` (nové nahradí předchozí) a argument kliknutí `ToastLaunchArgument.Settings` (`settings=general`, jediný argument mimo `printer=…`, který `IsWellFormed` přijme); `ToastActivationRouter` ho neposílá na web, ale přes opener, který připojí UI (`AttachSettingsOpener`), otevře okno Nastavení na záložce Obecné. Klik před připojením UI (čekání na displej, T-099) se podrží a vyřídí po připojení.
5. Kliknutí na toast vrátí argument s id tiskárny; `App/Notifications/ToastActivationRouter` (také `IMonitoringObserver`) ho přeloží na aktuálně nastavenou tiskárnu a otevře její web přes `PrinterWebAddress` a `IUrlLauncher`. Kliknutí přichází dvěma cestami: událost `Activated` živého toastu (banner) a COM aktivátor toastů (T-068: `Platform/Windows/ToastActivatorServer`, `INotificationActivationCallback` přes `[GeneratedComClass]`, CLSID ve vlastnosti zástupce `System.AppUserModel.ToastActivatorCLSID` a registrace `HKCU\Software\Classes\CLSID\{clsid}\LocalServer32`). Jen přes aktivátor Windows hlásí kliknutí v centru oznámení a jen přes něj aplikaci spustí, když neběží (`-ToastActivated`/`-Embedding`). Spuštění kvůli kliknutí nejdřív zaregistruje aktivátor, počká na kliknutí (`ToastActivationInbox`) a pak ho buď předá běžící instanci příkazem `toast:<argument>` (T-043), nebo ho zpracuje samo, až aplikace běží. Router opakované hlášení téhož kliknutí do 2 s ignoruje a kliknutí, které aplikaci spustilo, počká na první nastavení monitoringu.
6. Historie telemetrie (T-012): `Core/History/TelemetryHistory` drží pro každou tiskárnu v paměti kruhový buffer vzorků (`TelemetrySample`, 48 B, bez objektů na haldě) za posledních 24 h, bez ukládání na disk. Plní ho `App/History/TelemetryHistoryObserver` ze `SnapshotUpdated` a při každém běhu mu předá tiskárny a interval. Graf teplot (T-011) čte rozsah přes `CopySamples` do vlastního bufferu a překresluje jen při změně `GetVersion` / události `Changed`.
7. Okno diagnostiky (T-011) z tray menu: `App/Diagnostics/DiagnosticsViewModel` vzniká při otevření okna a při zavření se uvolní (odhlásí se od `IPrinterMonitor` a `MonitoredPrinters`). Historii odebírá jen graf: k `TelemetryHistory.Changed` se přihlásí při připojení do okna, a jen když je viditelný on i všichni jeho předkové (T-084); odhlásí se při zavření okna nebo skrytí. Zavřené nebo skryté okno tak nic nestojí (minimalizované okno se počítá jako zobrazené). Tiskárny aktuálního běhu bere z `App/Tray/MonitoredPrinters` (`IMonitoringObserver`), informace o tiskárně a firmwaru z `IPrinterInfoSource` (PrusaLink `/api/version` + `/api/v1/info`). Graf `App/Diagnostics/Chart/TemperatureChart` je vlastní Avalonia control; přípravu dat (kopie, decimace na sloupce pixelů, přerušení čar) dělá `TemperatureChartData` bez Avalonie. Jediná instance okna a jeho zavření při ukončení aplikace řeší `App/Windows/AuxiliaryWindowSlot` (stejně pro okno O aplikaci).

8. Více tiskáren (T-013): jedna agregovaná ikona. `App/Tray/TrayStatusRules` vybírá nejzávažnější tiskárnu (chyba > vyžaduje zásah > offline > pozastaveno > tiskne > zaneprázdněna > hotovo > nečinná; při shodě první v konfiguraci), tooltip má pro víc tiskáren jeden řádek na tiskárnu (nejzávažnější první, při nedostatku místa „Další tiskárny: N“). V menu má každá tiskárna vlastní podmenu, i když je jen jedna (T-042, dřív byla jedna tiskárna plochou položkou a kliknutí na ni otevřelo web): „Otevřít PrusaLink“ / „Otevřít Prusa Connect“ a u tiskárny se zapnutou kamerou „Zobrazit kameru“ / „Skrýt kameru“ (obyčejná položka, text podle toho, zda je okno kamery otevřené; od 2026-10-22 místo zaškrtávací „Kamera“). S otevřeným oknem kamery je nad „Skrýt kameru“ ještě „Zobrazit kameru“, která okno přivede dopředu (T-102, macOS i Windows, i okno navrchu bez ikony v Docku / tlačítka na hlavním panelu). Řádek tiskárny jen otevírá podmenu. „Diagnostika…“ je jediná globální položka hlavního menu nad „Nastavení…“ (rozhodnutí uživatele 2026-10-21; okno má vlastní výběr tiskárny, už otevřené okno si tiskárnu ponechá). Povolená je jen tehdy, když menu ukazuje tiskárny; při „Spouštění…“, po selhání monitorování a bez tiskárny je zakázaná. Celé platformní menu se přestaví jen při změně jazyka (`FixedItemsChanged`). Přepnutí povolení „Diagnostika…“ změní jen tuto jednu položku na místě (`FixedItemChanged` → `ITrayMenuTarget.UpdateFixedItem`, rozhodnutí uživatele 2026-10-21), takže otevřené menu se nezavře ani nepřestaví; při dotazu na tiskárnu se pevné položky nemění vůbec. Bez tiskárny menu ukáže zakázaný text „Není nastavena žádná tiskárna“ a „Přidat tiskárnu…“ (otevře nastavení na záložce Tiskárny a přidá tiskárnu, `SettingsViewModel.AddPrinterFromTray`). Název tiskárny se v menu zkracuje na 32 znaků, celý je v tooltipu položky. Pevné položky a položky podmenu mají klávesové zkratky z `.resx` (`_`), tiskárny žádné (`NativeMenuText.EscapeAccessKeys`, obchází chybu `AccessText` v Avalonii 12). Dotaz jedné tiskárny stojí O(1) v menu a O(n) bez alokace u ikony; text se formátuje a menu mění jen při viditelné změně, strukturu menu mění jen změna sady tiskáren.

9. Okno nastavení (T-015) z tray menu: `App/Settings/SettingsViewModel` (+ `PrinterEditorViewModel` pro každou tiskárnu) vzniká při otevření okna a při zavření se uvolní (zruší rozběhnutý test spojení, zapomene napsaná hesla). Načítá a ukládá přes `ISettingsEditorStore` (`SettingsEditorStore`): nejdřív nová hesla do `ISecretStore` (s možností vrátit předchozí hodnotu), pak atomicky `settings.json`; při chybě se zapsaná hesla vrátí. Po uložení `ISettingsApplier` (= `MonitoringSession.ApplyAsync`) zruší běžící běh monitoru a spustí nový s novým nastavením; pozorovatelé (ikona, menu, notifikace, historie) dostanou nastavení přes `ApplySettings` a stav tiskáren se stejným id, adresou a typem připojení si ponechají. Když se tiskárny ani interval nemění (jen upozornění), monitor běží dál a pozorovatelé dostanou jen `UpdateSettings`. Hesla odebraných tiskáren se mažou až po uložení a po skončení předchozího běhu monitoru; snapshot, který doběhne po požadavku na zastavení běhu, se nepublikuje. „Otestovat spojení“ (`PrusaLinkConnectionTester`) volá `PrusaLinkClient.GetInfoAsync` s neuloženými hodnotami formuláře, napsané heslo předá klientovi jen v paměti. Důvod chyby vrací PrusaLink klient jako `PrusaLinkFailure`.

10. Jazyk aplikace (T-029): `AppSettings.Language` (kód z `Core/Settings/AppLanguages`, `null` = podle systému) se ukládá do `settings.json` jako `"language"`. Při startu `TrayHost.StartAsync` nejdřív načte nastavení (mimo UI vlákno), `App/Localization/UiLanguage` nastaví `Strings.Culture` a teprve pak vzniknou tray view modely, menu a tooltip; `MonitoringSession.Start(settings)` už nastavení znovu nenačítá. Za běhu jazyk aplikuje `UiLanguageObserver` (první `IMonitoringObserver`, `ApplySettings` i `UpdateSettings`) na UI vlákně. Texty v XAML jsou vázané přes `LocalizedStrings` (`{Binding [Klíč], Source={x:Static loc:LocalizedStrings.Instance}}`, kompilovaný indexer binding, slabý odběr), takže se otevřená okna přepnou sama; texty, které formátují view modely, přeformátuje `ILanguageAware.RefreshTexts` (tray přes `TrayHost`, otevřená okna přes `AuxiliaryWindowSlot.RefreshTexts`). `CurrentCulture` (čísla, data) se nemění.

9. Otevření webu PrusaLink přihlášený (T-028): `App/Tray/Menu/PrinterWebOpener` získá adresu z `Core/Web/IPrinterWebGateway.OpenAsync`. Výsledek `PrinterWebAccess` je buď adresa proxy (`IsProxied`), nebo holá adresa tiskárny s důvodem (`PrinterWebFallback`). Brána se volá mimo UI vlákno, jen když položka menu ukazuje aktuální adresu své tiskárny. Adresu proxy otevře `IUrlLauncher.OpenSecretAsync`, který do logu nezapíše adresu ani text výjimky (`Process.Start` do něj vkládá celou adresu s tokenem). Při záložní cestě se otevře holá adresa bez další notifikace a do logu jde jen název důvodu. Po uloženém nastavení zastaví `SettingsEditorStore` proxy odebraných tiskáren a tiskáren se změněnou adresou, jménem, typem připojení nebo heslem (`StopAsync`, souběžně s restartem monitoringu, nejvýš 5 s, před smazáním hesel odebraných tiskáren). Při ukončení aplikace `TrayHost` zavolá `StopAllAsync` (čeká nejvýš 1 s souběžně se zastavením monitoringu) a pak kontejner DI bránu uvolní přes `DisposeAsync`. Implementace `PrusaLink/WebProxy/PrusaLinkWebGateway` (registrovaná v `AddPrusaLink`) spouští líně pro každou tiskárnu vlastní lokální reverzní proxy. Proxy je Kestrel ze sdíleného frameworku ASP.NET Core na `127.0.0.1`, port `0`, má 256bitový token v první části cesty a kontroluje `Host`. Na Digest výzvy tiskárny odpovídá sama přes vlastní instanci `DigestAuthenticator`, takže heslo do prohlížeče nejde. Před otevřením prohlížeče proběhne přihlášený `GET /api/version`. Bez hesla, při odmítnutém heslu, nedostupné tiskárně nebo když proxy nejde spustit se otevře holá adresa. Proxy se zastaví po 10 minutách bez požadavku, přes `StopAsync`/`StopAllAsync` po změně nastavení tiskárny a při ukončení aplikace (`DisposeAsync`). Podrobnosti jsou v [api/prusalink.md](api/prusalink.md), oddíl „Lokální proxy“.

## Překryv okna kamery – widgety (plán T-076 až T-093)

Jediný `Border` s řádky z T-036 nahradil systém widgetů. Otázky rozhodl uživatel 2026-10-24, návrh T-076 je schválený. Core část (T-077) a framework v okně kamery (T-081) jsou hotové, jednotlivé widgety jsou **plán**.

- **Core (`Core/Cameras/Overlay`, T-077, hotovo):**
  - `CameraOverlayLayout` (`CameraSettings.Overlay`) je neměnný seznam `OverlayWidgetPlacement`. Každé umístění má textové id widgetu (`OverlayWidgetIds`), jednu ze 6 kotev `OverlayAnchor`, velikost `OverlayWidgetSize` S/M/L, zvýraznění a viditelnost.
    - Seznam je seřazený podle kotev. Pořadí v kotvě = pořadí v seznamu, od okraje okna ke středu.
    - Rovnost porovnává seznam po prvcích. Operace beze změny vrací stejnou instanci (levná detekce změn).
  - Každý typ widgetu je v rozložení nejvýš jednou (v1, bez ohledu na velikost písmen). Normální okno a celá obrazovka sdílejí jedno rozložení.
  - Výchozí rozložení `CameraOverlayLayout.Default` je podle návrhu T-076 3.3. Hlavní kotva `MainAnchor` = `BottomLeft` (kotva widgetu Časy).
  - Rozložení je **u tiskárny** v `printers[*].camera.overlay` jako `{ "widgets": [ { "id", "anchor", "size", "emphasized", "visible" } ] }`. Výchozí rozložení se nezapisuje.
    - „Použít u všech tiskáren“: `CameraOverlayLayout.ApplyToAll` / `AppSettings.WithCameraOverlayLayoutForAllPrinters`.
    - Neznámé id widgetu se zachová a zapíše zpět. Známý widget, který v seznamu chybí, se doplní na výchozí místo.
    - Hodnoty sekce se čtou volně z `JsonElement`: chybný typ nebo neznámá hodnota = výchozí hodnota s jedním varováním bez opisu hodnot, ne poškozený soubor.
  - **Průhlednost pozadí karet** je jediná **globální** hodnota `AppSettings.CameraOverlayOpacityPercent` (`CameraOverlayOpacity`, 30–95 %, výchozí 72 %), v souboru `cameraOverlay.backgroundOpacityPercent`. Výchozí hodnota se nezapisuje.
  - `settings.json` má `version` 2. Starý tvar T-036 (`corner` / `normal` / `mini`) bez `widgets` se při načtení převede a už se nezapisuje:
    - viditelnost starých položek se zahodí, začíná se z výchozího rozložení,
    - starý roh určí, kam se výchozí rozložení zrcadlí (`CameraOverlayLayout.FromLegacyCorner`, `OverlayAnchors.MirrorBetweenCorners`): hlavní kotva skončí ve starém rohu a s ní celý levý sloupec,
    - do logu jde jedna informační zpráva bez hodnot (`SettingsLoadResult.Notices`).
  - Operace nad rozložením jsou čisté funkce bez Avalonie: `InAnchor`, `MoveTo` (kotva a pozice v kotvě), `WithSize`, `WithEmphasized`, `WithVisible`, `ResetToDefault` (neznámé widgety ponechá), `Mirrored`.
  - Mimo okno nastavení zapisuje rozložení `ICameraOverlayLayoutWriter` / `CameraOverlayLayoutWriter` přes `ISettingsStore.SetCameraOverlayLayoutAsync`. Ten bajtově přepíše jen sekci `overlay` dané tiskárny (`CameraOverlaySectionWriter`, po vzoru `CameraMonitorPathWriter`), výchozí rozložení jako `{}`.
    - Po zápisu přijde událost `LayoutSaved` (id tiskárny + rozložení). Otevřené okno nastavení z ní převezme jen rozložení dané tiskárny (`AppSettings.WithCameraOverlayLayout`) a ostatní neuložené změny si ponechá (T-092).
    - `ConfirmAsync` + událost `LayoutConfirmed` (doplněno po review T-092): „Hotovo“ s konceptem rovným uloženému rozložení. Když soubor mezitím drží jiné rozložení, zapíše a ohlásí `LayoutSaved`, jinak nic nezapíše a ohlásí `LayoutConfirmed`. `LayoutSaved` se tak dál vyvolá jen po zápisu.
  - Stará podzáložka Překryv (T-036), `CameraSettings.LegacyOverlay` a typy `CameraOverlayOptions` / `CameraOverlayItems` / `CameraOverlayCorner` zanikly s T-092. Převod starého souboru (T-077) čte starý roh přímo z JSON a typy nepotřebuje.
- **Záložka Widgety v nastavení (T-092, hotovo, `App/Settings/Widgets`, `SettingsViewModel.Widgets.cs`):**
  - Hlavní záložka hned za Tiskárnami; výběr tiskárny sdílí `SettingsViewModel.SelectedPrinter` se záložkou Tiskárny. Seznam = registrované widgety v pořadí registrace (`WidgetItemViewModel`), viditelnost jde přes `CameraOverlayLayout.WithVisible` do rozpracovaného rozložení tiskárny (`PrinterEditorViewModel.OverlayLayout`), neznámé widgety rozložení zůstanou.
  - Smlouva T-081 rozšířená o `DescriptionKey`, `IconKey` a `IOverlayWidgetSettingsFactory? Settings` (výchozí členy rozhraní / `init` vlastnosti). Továrna vytvoří `OverlayWidgetSettingsViewModel` pro vybranou tiskárnu přes úzké `IOverlayWidgetSettingsHost` (adaptér `SettingsViewModel` pro jednu tiskárnu) a uvolní ho při změně widgetu nebo tiskárny. Hodnoty a validace patří tiskárně. ## Pomocná okna Nastavení a Diagnostika – velikost a stav (T-094)

- Výchozí klient obou oken je **780 × 532 DIP**, minimum 640 × 400 (`AuxiliaryWindowPlacement.DefaultClientSize` / `MinClientSize`, shodné s XAML). Cíl: nejmenší běžná pracovní plocha notebooku ≈ 1093 × 580 DIP (1366 × 768 při 125 %, 1920 × 1080 při 175 %). Obě okna jdou maximalizovat (`CanMaximize`), minimalizovat ne.
- Velikost a stav maximalizace si každé okno pamatuje zvlášť v **`windows.json`** vedle `settings.json` (`App/Windows/AuxiliaryWindowStateStore`: `IAuxiliaryWindowStateStore`, `JsonAuxiliaryWindowStateStore`, bez datové složky `MemoryAuxiliaryWindowStateStore`). Je to stav aplikace, ne nastavení, se stejnými zásadami jako `camera-windows.json`: okno nastavení ho nezobrazuje ani neukládá, takže uložení nastavení ho nepřepíše; atomický zápis (dočasný soubor, pak nahrazení) na pozadí, opakování při zamčeném souboru (`FileRetry`), poškozený, příliš velký (> 64 KB) nebo neznámý / novější formát (`version` ≠ 1) = výchozí hodnoty a další zápis soubor nahradí; vytvoření úložiště nesahá na disk. `System.Text.Json` jen přes `AuxiliaryWindowsJsonContext`. Soubor čte `TrayHost.StartAsync` souběžně s nastavením (čeká nejvýš 1 s) a při ukončení počká na rozběhnutý zápis.
- Formát: `{"version": 1, "windows": {"settings": {"width": 1000, "height": 640, "maximized": true}, "diagnostics": {"maximized": false}}}` – `width`/`height` = klient v DIP v normálním (nemaximalizovaném) stavu; chybí, dokud velikost nezměnil uživatel. **Poloha se neukládá**, okno se dál centruje (`CenterScreen`) na monitoru, kde se otevírá.
- Při otevření (`WorkAreaFitter.Remember`, volá `AuxiliaryWindowFactory`): uložená velikost (neplatná → výchozí, menší než minimum → minimum, `AuxiliaryWindowPlacement.PreferredClientSize`) se vždy prožene `AuxiliaryWindowPlacement.Fit` na pracovní plochu monitoru, kde se okno otevírá; uložená maximalizace → okno se otevře maximalizované a obnoví se na tuto (přizpůsobenou) velikost.
- Při zavření (jakkoli, i „Zrušit“ v Nastavení) se uloží stav z `AuxiliaryWindowSizeMemory` (čistá třída): jen velikost, kterou dal oknu uživatel v normálním stavu. Velikost nastavená aplikací (přizpůsobení pracovní ploše před zobrazením a po otevření), změna kvůli DPI a velikost maximalizovaného okna se nepočítají, takže okno zmenšené jen kvůli malé obrazovce si ponechá větší preferenci uživatele. Windows hlásí maximalizovanou velikost dřív než nový stav; tato poslední změna se při přechodu do maximalizace vrátí.

**Místní síť na macOS (T-097):** Core zná jen neutrální „žádná cesta k adrese“: `PrinterProblem.HostUnreachable` (PrusaLink při `SocketException` s `SocketError.HostUnreachable`, `PrusaLinkFailure.HostUnreachable`) a `CameraFeedException.IsHostUnreachable` → `CameraStatus.IsHostUnreachable` (FFmpeg `AVERROR(EHOSTUNREACH)` s číslem errno daného OS). Zda za tím může být oprávnění, rozhoduje App přes `ILocalNetworkPrivacy`: na macOS 15+ `MacLocalNetworkPrivacy` (jen adresy v místní síti podle `LocalNetworkAddress`: soukromé a link-local rozsahy IPv4/IPv6, multicast, broadcast, názvy `.local` a jednoslovné; loopback nikdy), jinde `NoLocalNetworkPrivacy`. Hlášku ukazuje okno diagnostiky (detail stavu), „Otestovat připojení“ a test kamery v nastavení a stavový řádek okna kamery; `LocalNetworkPrivacyObserver` zapíše řádek do logu i bez otevřeného okna (jednou za tiskárnu / kameru a běh, bez adresy). macOS neumí stav oprávnění přečíst, proto text říká „možná“. U hlášky v diagnostice a u výsledku „Otestovat připojení“ a testu kamery je tlačítko „Otevřít Nastavení systému“ (`ILocalNetworkPrivacy.OpenSettings`): `MacLocalNetworkPrivacy` otevře přes `Action<Uri>` (stejný šev jako T-020, v aplikaci `MacSystemSettings.Open`, v testovacím režimu jen zápis do logu, testy používají falešné implementace) `x-apple.systempreferences:com.apple.settings.PrivacySecurity.extension?Privacy_LocalNetwork` a když macOS adresu odmítne, panel Soukromí a zabezpečení bez kotvy.

Výběr platformní implementace (`ISecretStore`, `INotificationService`) probíhá v composition rootu v App podle OS (explicitní registrace kvůli Native AOT); registraci `ISecretStore` zavedl T-007 (`Composition/AppServices`): Windows → `WindowsCredentialSecretStore`, macOS → `KeychainSecretStore` (T-021), ostatní OS → `UnsupportedSecretStore` (hesla nedostupná, aplikace běží dál). Testovací režim (T-044) používá na macOS vždy `TestModeSecretStore` v paměti, Keychain uživatele nepoužije.

**Keychain na macOS (T-021, rozhodnuto 2026-10-29):** položky jsou v souborovém login Keychainu (výchozí cíl SecItem API; funguje s ad-hoc podpisem). Jsou čitelné, jen když je login Keychain odemčený, a jsou součástí záloh Time Machine i přenosu přes Migration Assistant. Atribut `kSecAttrAccessible` se nenastavuje, protože ho login Keychain neuplatňuje. *Data protection keychain* by vyžadoval Developer ID s provisioning profilem (T-060). macOS smí zobrazit vlastní dialog (odemknutí Keychainu, „povolit přístup“ po aktualizaci ad-hoc sestavení). Každé volání Keychainu proto běží na thread poolu (`Task.Run` v `KeychainSecretStore`), takže ani čekající dialog nezablokuje UI vlákno, okna ani menu v liště. Dialogy vypíná jen testovací fixture pro vlastní proces, produkční kód nikdy. `INotificationService` (T-010, T-020): Windows → `ToastNotificationService`, macOS → `UserNotificationService` (jen když `Program.Main` otevřel centrum notifikací pro povolený bundle identifikátor), jinak `NullNotificationService`. Úkoly s `platform: macos` se implementují až na Macu a Windows úkoly na nich nezávisí.

Konkrétní volby jsou otevřené otázky v příslušných úkolech (T-010, T-017, T-019, T-020, T-021, T-055, T-056).

### Start na macOS bez aktivního displeje (T-096, T-099, rozhodnuto 2026-10-29)

Avalonia.Native při inicializaci platformy vytváří `CVDisplayLink` a bez aktivního displeje skončí chybou -6661; platformu nejde v procesu inicializovat podruhé (podrobně T-096). `Program.Main` proto na macOS před startem Avalonie čeká na aktivní displej (`StartupDisplayWait`, kontrola `CGGetActiveDisplayList` každou 1 s, bez časového limitu). Během čekání běží služby aplikace (rozhodnutí uživatele 2026-10-29), UI se k nim připojí po probuzení:

- **Rozdělení kompozice:** `Composition/ServiceHost` vlastní kontejner služeb (nastavení, Keychain, monitoring `MonitoringSession`, detekce událostí, notifikace, proxy webu tiskárny) a nepotřebuje žádný objekt UI; `ServiceHost.CreateAsync` načte nastavení a použije jazyk, `StartMonitoring` spustí sledování (jednou). `TrayHost` jen přidá objekty menu baru/oznamovací oblasti (`TrayHost.Attach`) a při ukončení je uvolní před `ServiceHost.StopAsync`. Běžný start (i Windows) volá obojí hned za sebou v `App` ve stejném pořadí jako dřív (`TrayHost.StartAsync`).
- **UI vlákno před Avalonií:** view modely a pozorovatelé posílají práci na UI vlákno přes `IUiDispatcher`. Před Avalonií je to `Tray/StartupUiDispatcher` (fronta pro hlavní vlákno), ke kterému patří `StartupSynchronizationContext` hlavního vlákna, takže pokračování `await` služeb spuštěných na hlavním vlákně se na něj vrací jako na UI vlákno. `App.OnFrameworkInitializationCompleted` jako první zavolá `StartupUiDispatcher.AttachTo(AvaloniaUiDispatcher)`: co čekalo, proběhne hned (stejné vlákno), další práce jde na dispatcher Avalonie, pořadí se zachová. Služby tak mají po celou dobu jedno UI vlákno – hlavní vlákno.
- **Hlavní vlákno během čekání** nespí: `Platform/StartupLoop` střídá práci z fronty a běh `CFRunLoop` hlavního vlákna (`Platform/MacOS/MacStartupRunLoop`: `CFRunLoopRunInMode` ve výchozím režimu s vlastním zdrojem `CFRunLoopSource` pro probuzení, `[LibraryImport]`, AOT safe). Tím se obsluhuje i hlavní dispatch fronta (zpětná volání centra notifikací). Bez Core Foundation (nikdy neviděno) náhradní `ManagedStartupRunLoop` obsluhuje jen frontu.
- **Orchestrace:** `Composition/DisplayWaitStartup<TServices>` (obecná kvůli testům s fakes): s aktivním displejem nic nespouští (běžný start), jinak při první kontrole bez displeje spustí služby (`Program.StartServicesAsync`), čeká a vrátí běžící `ServiceHost` (`EarlyServices`), ke kterému se `App` připojí; při SIGTERM/SIGINT služby zastaví (nejdéle 5 s) a `Main` vrátí 0. Selhání startu služeb ukončí čekání výjimkou jako dřív selhání startu UI.
- **Příkazy instancí a kliknutí na oznámení:** centrum notifikací se otevírá před čekáním (delegát musí existovat dřív, než AppKit dokončí spuštění). Během čekání a předávání (do konce `App.StartHost`) má `InstanceCommandQueue` prozatímní obsluhu (`AttachProvisional`, `SingleInstance/WaitingInstanceCommands`), která vrací, zda příkaz vyřídila: klik na oznámení otevře web tiskárny hned přes `ServiceHost.ActivateToast` (jako klik, který aplikaci spustil); testovací „quit“ (Debug, testovací režim) během čekání čekání ukončí. Vše ostatní – hlavně „activate“ druhého startu (rozhodnuto 2026-10-29) a „quit“ po skončení čekání – fronta podrží (sloučené, každý příkaz čeká nejvýš jednou) a doručí obsluze `App`, jakmile ji `App` připojí; nic se nezahodí ani nedoručí dvakrát.
- **Test na vyžádání:** Debug přepínač testovacího režimu `LAYERPEEK_TEST_NO_DISPLAY_MS` (`AppEnvironment.TestNoDisplay`, jen s testovací datovou složkou, v Release neexistuje) nechá `PretendedNoDisplay` hlásit „žádný aktivní displej“ po danou dobu; `MacDisplayWaitE2ETests` (`LAYERPEEK_E2E=1`) tak spustí skutečnou Debug aplikaci v testovacím bundlu proti simulátoru na 127.0.0.1 bez uspání displeje.
- **Windows** nečeká nikdy; `EarlyServices` je tam vždy `null`.

### Izolace testů na macOS (T-095, rozhodnuto 2026-10-28)

Testy (`dotnet test`, E2E i ruční testovací běhy Debug sestavení) nesmí na macOS měnit stav skutečného uživatele. Zakázané je zapisovat do:
- `~/Library/Application Support/LayerPeek` (nastavení, data) a `~/Library/Logs/LayerPeek` (logy) – testovací režim má vlastní datovou složku (`LAYERPEEK_TEST_DATA_DIR`, jen Debug, `AppEnvironment`);
- `~/Library/LaunchAgents` a Login Items (`SMAppService`) – autostart v testovacím režimu jen náhradou v testovací datové složce (`LoginItems/LayerPeek.loginitem`, `AppEnvironment.TestLoginItemPath`, `StandInLoginItem`), obdoba `AppEnvironment.AutostartShortcutPath` na Windows (T-019). Skutečný Login Item dostane jen produkční aplikace ve svém `LayerPeek.app`, nikdy testovací režim ani testhost (`AppServices.CreateMacAutostart`). Úklid po pádu: náhrady leží jen ve vyhrazených testovacích složkách, které se mažou na začátku každého běhu testů (`ReservedTempDirectory.SweepAsync`), a Debug-only režim `--layerpeek-e2e-clear-autostart` (s `LAYERPEEK_TEST_DATA_DIR`) smaže náhrady autostartu v dané testovací složce a skončí; na skutečný Login Item ani na složku Po spuštění nesáhne;
- Keychainu mimo vyhrazený testovací prefix (nikdy produkční `LayerPeek`); pozůstatky s testovacím prefixem se uklidí i po spadlém běhu (T-021). Integrační testy `KeychainSecretStore` zapisují jen pod službu `LayerPeek.Tests/<guid>`; assembly fixture `LayerPeek.App.Tests` před prvním a po posledním testu smaže všechny položky pod `LayerPeek.Tests` a vypne dialogy Keychainu pro testovací proces (`SecKeychainSetUserInteractionAllowed`), takže test nikdy nečeká na dialog. Zamčený login Keychain (odemknout by šel jen dialogem) testy, které zapisují, přeskočí s důvodem;
- notifikací pod produkčním bundle identifikátorem – testy používají vlastní identifikátor (např. s příponou `.E2E`), doručené testovací notifikace se uklidí při ukončení i v režimu úklidu po pádu, oprávnění produkčního identifikátoru se nemění (T-020). Provedení: `AppEnvironment.NotificationBundleIdentifier` povolí jen jeden identifikátor (produkce `io.github.pfoltynek.LayerPeek`, testovací režim s `LAYERPEEK_TEST_TOASTS=1` jen `io.github.pfoltynek.LayerPeek.E2E`, jinak žádný) a centrum notifikací se otevře, jen když běžící bundle má přesně ten identifikátor (`MacMainBundle` přes CoreFoundation; bez bundlu se `currentNotificationCenter` vůbec nevolá). Běžný `dotnet test` žádný bundle nestaví a o oprávnění nežádá (falešné centrum `FakeUserNotificationCenter`). Skutečné notifikace ověřuje jen E2E test na vyžádání `MacNotificationsE2ETests` (`LAYERPEEK_E2E=1`), který sestaví Debug `LayerPeek E2E.app` s identifikátorem `.E2E` v `artifacts/` (ne v dočasné složce: tam macOS notifikace odmítne) a po sobě uklidí notifikace, registraci v LaunchServices, doménu předvoleb i bundle. **Známý pozůstatek, nemaže se:** položka „LayerPeek E2E“ v Nastavení systému → Oznámení (macOS na ni nemá žádné rozhraní ani nástroj, databáze `usernoted` je chráněná TCC; ověřeno 2026-10-29);
- sdílených složek mimo `$TMPDIR` – sockety, zámky a testy práv a vlastnictví běží v soukromé podsložce `$TMPDIR` a po sobě ji smažou. Repozitář může ležet na svazku s `noowners` (vlastnictví se nevynucuje), takže testy práv v něm nejsou průkazné (T-053).

Týká se `~/Library/Application Support/LayerPeek` a `~/Library/Logs/LayerPeek` (Windows `%APPDATA%\LayerPeek` a `%LOCALAPPDATA%\LayerPeek\logs`, ne celé `%LOCALAPPDATA%\LayerPeek`, kde může být nainstalovaná aplikace).

## Logování

Aplikace loguje přes `Microsoft.Extensions.Logging` a `[LoggerMessage]`; jediný provider je vlastní souborový `FileLogProvider` (T-024, `App/Logging`, bez NuGet balíčku, kompatibilní s Native AOT).

- **Umístění:** Windows `%LOCALAPPDATA%\LayerPeek\logs`, macOS `~/Library/Logs/LayerPeek` (`AppDataPaths.GetDefaultLogDirectory`, vystavené jedním místem `AppEnvironment.LogDirectory()`). Testovací režim T-044 zapisuje do `logs` v testovací datové složce. Bez složky pro logy (OS ji neposkytne) aplikace běží dál, jen bez logu.
- **Formát:** `2026-10-21 14:03:12.345 +02:00 INF [pid 12345] Kategorie: zpráva`, úrovně `TRC DBG INF WRN ERR CRT`. Výjimka celá (`ToString()`, se stack trace) a další řádky zprávy pokračují na řádcích odsazených čtyřmi mezerami, takže každý neodsazený řádek je začátek záznamu. UTF-8 bez BOM, konce řádků `\n`.
- **Úroveň:** výchozí `Information`, v testovacím režimu `Debug`. Rozhoduje jen `LogLevelSwitch` (čtený při každém volání), takže úroveň jde přepnout za běhu bez nové factory. Volbu „Podrobné logování (Debug)“ v nastavení (T-047, `AppSettings.DebugLogging`) uplatňuje `DebugLoggingObserver`: načtené nastavení a každé uložení přepne úroveň na `Debug` / `Information` a změnu zaloguje. Do načtení nastavení a vždy u druhého spuštění platí `Information`, testovací režim zůstává na `Debug`.
- **Zápis:** volající jen naformátuje záznam a vloží ho do omezené fronty (10 000 záznamů); jedno vlákno na pozadí (ne thread pool) ji zapisuje po dávkách. Plná fronta nové záznamy zahodí. Když zápis dávky selže (plný disk, práva, druhý proces drží zámek souboru déle než 2 s), dávka se ztratí, ale aplikaci to neshodí. Počet ztracených záznamů uvede log v další úspěšné dávce. Smazaná složka se vytvoří znovu. `Flush(timeout)` počká na vše dosud zalogované (ukončení, T-046).
- **Dvě instance (T-043):** obě zapisují do stejného souboru. Každá dávka se zapíše jedním voláním na skutečný konec souboru pod pojmenovaným mutexem souboru (`FileMode.Append` v .NET by psal na vlastní pozici). Na Windows je mutex v globálním jmenném prostoru, protože týž uživatel přihlášený dvakrát (konzole + vzdálená plocha) má v každé relaci primární instanci, ale jeden soubor v `%LOCALAPPDATA%`. Záznam, který zůstal po přerušeném zápisu bez konce řádku, dostane `
` dřív, než se připíše další; soubor se otevírá na každou dávku se sdílením `ReadWrite | Delete`, takže ho nikdo nezamkne a po rotaci se píše vždy do aktuálního souboru.
- **Rotace:** podle velikosti, 1 MB × 5 souborů (`LayerPeek.log`, `LayerPeek.1.log` … `.4.log`, nejstarší se přepíše). Rotuje jen primární instance (zapne ji `Program.Main` po `SingleInstanceGuard`). Aktuální soubor se nejdřív jedním přejmenováním odsune na `LayerPeek.rotating.log`, teprve pak se posunou starší soubory (jen po první mezeru). Když aktuální soubor nejde přejmenovat (otevřený bez sdílení mazání), nic se nezmění a rotace se zkusí při dalším zápisu, aniž by přišel o starší soubory. Rotaci přerušenou pádem dokončí primární instance hned při prvním zápisu.
- **Životnost:** `AppLogging` (factory + provider) vzniká v `Program.Main` hned po `NativeLibrarySearch.Restrict()` a před `SingleInstanceGuard`, `Main` ho uvolní až po návratu z Avalonie. `App` ho předá `TrayHost`; kontejner DI factory nevlastní. `App.OnDesktopExit` jen vyprázdní frontu (při konci relace OS se `Main` nemusí dokončit). Po uvolnění se pozdní záznamy tiše zahodí.
- **Neošetřené výjimky (T-046):** `UnhandledExceptionLogger` se registruje v `Program.Main` hned po vytvoření logování (platí i pro druhé spuštění): `AppDomain.UnhandledException` (`Critical`, celá výjimka), `TaskScheduler.UnobservedTaskException` (`Error`, bez `SetObserved`) a po startu Avalonie `Dispatcher.UIThread.UnhandledException` (`Critical`, bez `Handled`). Výjimku z UI vlákna, kterou pak ukončující proces hlásí znovu, zapíše jen jednou. Po zápisu vyprázdní frontu logu (nejvýš 2 s) a sám nikdy nehází. Chování při pádu se nemění. Debug build má pro E2E testy testovací příkaz `crash:ui|background|task`.
- **Tajné údaje:** provider nic nemaskuje; volající nikdy nelogují hesla, klíče ani tokeny a adresy s přihlašovacími údaji redigují (`UriRedaction`).
- **Podpora (T-048, T-049):** okno O aplikaci nabízí uložení diagnostického balíčku, kopírování informací do schránky (`SupportText`: `SupportInfo` a posledních 200 řádků logu z `LogTail`, nejvýš asi 64 KB) a otevření složky s logy (`App/Support`). `SupportActions` vezme nastavení aktuálního běhu (před prvním během uložené), stavy tiskáren z `IPrinterMonitor` a log procesu (`SupportLog`: složka a `Flush`). `SupportInfo` sestaví anglický přehled (`info.txt`), `SettingsExport` (Core) nastavení bez dotazové části adres kamer a `SupportBundle` ZIP z logů (čtených se sdílením), `info.txt` a `settings.json`. Nedokončený ZIP se smaže. `UriRedaction.Redact` maskuje kromě přihlašovacích údajů i dotaz a fragment adresy (`?***`, `#***`), protože mohou nést token. Uživatelský návod je v [troubleshooting.md](troubleshooting.md).
